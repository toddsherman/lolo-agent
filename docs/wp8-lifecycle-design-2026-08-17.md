## 1. The finding, restated in the terms the code supports

Roadmap §21 states the class: *the hypothesis layer's lifecycle is driven
by its own budget counters, while the moments that decide outcomes are
generated by the incumbent's archive and stagnation machinery.* That is a
claim about two clocks. This section fixes what each clock actually is, so
the rest of the document can reason about alignment rather than about
metaphor.

**The incumbent's clock** is the event stream of `decide()`
(`neural_planner.py:21102`): committed decisions, archive deposits,
stagnation restores, life-loss recoveries, goal-exhaustion rollbacks,
option searches and their deferrals, milestone collections. It is
irregular, and its irregularity is load-bearing — §4.50 measured that the
excursions which look wasteful are what deposit the archive ladder later
progress climbs.

**The hypothesis layer's clock** is `HypothesisPlan.active_decisions`
(`relational_planner.py:396`), an integer incremented once per
`advance()` call and compared against
`TerminationCondition.decision_budget` (`relational_planner.py:254`). It
is regular by construction and it is decoupled from everything the
incumbent's clock measures except the bare fact that a transition
occurred.

E6's proximate cause is exactly a phase error between the two, and it is
three events wide (§4.53, design §16.4). This document treats the phase
error as the object of study, not the individual seam that tripped over
it.

## 2. Q1a — The hypothesis layer's state machine, enumerated

### 2.1 The states

There is no explicit state enum. The layer's state is the tuple

```
(relational_plan is None?, plan.active_id, plan.achieved_ids,
 plan.active_decisions, plan.hypotheses, plan.remaining_milestone_cells)
```

held on the monolith at `neural_planner.py:1322`
(`self.relational_plan: Optional[RelationalHypothesisPlan]`), and the
per-hypothesis kind at `relational_planner.py:144` (`HypothesisKind`:
`establish_configuration`, `hold_configuration`,
`exploit_configuration`). Reduced to the states that matter for liveness:

| State | Predicate | What the seams see |
| --- | --- | --- |
| **NO PLAN** | `self.relational_plan is None` | every seam fails open; `_relational_navigation_objective()` → `None` (`:19985`) |
| **ACTIVE-ESTABLISH** | `active.kind is ESTABLISH_CONFIGURATION` | restore-archive preference live (`_relational_restore_preference:19849`); navigation seams inert (realization kind is `restore_archive` / `reproduce_transition`, so `objective_target_cells` returns `()`) |
| **ACTIVE-HOLD** | `active.kind is HOLD_CONFIGURATION` | realization kind **is** `reach_cells_under_hold`, but `payload["target_cells"] = ()` by construction (`relational_planner.py:1209`) ⇒ `objective_target_cells` → `()` ⇒ **every navigation seam inert** |
| **ACTIVE-EXPLOIT** | `active.kind is EXPLOIT_CONFIGURATION` | the only state in which certified cells are published: S1 commit tier, S2 restore key, S3 deposit gate all live |
| **TERMINAL** | `advance()` returned a terminal outcome | `self.relational_plan = result.plan if result.plan.active_id else None` (`:19845`) ⇒ almost always NO PLAN |

**The single most consequential structural fact in this table**:
ACTIVE-HOLD and ACTIVE-EXPLOIT share a realization *kind* but not a
payload, so the entire navigation-seam family is live in exactly one of
the three active states. There is no partial-liveness state.

### 2.2 The transitions, and what drives each today

`propose` (`relational_planner.py:1283`) and `advance`
(`relational_planner.py:1420`) are the only transition functions. Both are
pure; the drivers are entirely on the monolith side.

| # | Transition | Function / site | Driven by |
| --- | --- | --- | --- |
| T1 | NO PLAN → ACTIVE-* | `propose` via `_relational_propose_and_log:19681`, called once at `decide():21131` | **The decision counter.** The hook runs at the top of every `decide()` **after** `_restore_after_life_loss` returns `None` (`:21129`), and early-returns while a plan already has an `active_id` (`:19694–19698`). One activation instant per decision, at the top. |
| T2 | ACTIVE-* → ACTIVE-* (continue) | `advance` → `ADVANCE_CONTINUE`, `exhaust_or_continue:1526` | **A verified transition**, of either summary kind. Increments `active_decisions` by 1. |
| T3 | ACTIVE-ESTABLISH → ACTIVE-HOLD | `achieve_and_activate(realized=True)` when `configuration_maps(...)` (`:1554`, `:1463`) | **A verified configuration signature** matching the target. This is the one transition genuinely driven by a verified world fact. |
| T4 | ACTIVE-HOLD → ACTIVE-EXPLOIT | `achieve_and_activate(realized=False)` when the hold has successors (`:1587`) | **One verified transition of any kind**, plus successor-initiation. Held-across-*one*-transition is the whole predicate. |
| T5 | ACTIVE-EXPLOIT → TERMINAL(achieved) | `reached or collected_hit` (`:1616`) | **A verified player cell in `target_cells`, or a collection of one.** The other genuinely world-driven transition. |
| T6 | ACTIVE-* → TERMINAL(`budget_exhausted`) | `exhaust_or_continue` (`:1527–1535`), `_terminate_chain:1386` | **A decision count**: `plan.active_decisions + 1 >= active.termination.decision_budget`. All three kinds take `decision_budget=config.decision_budget` (`relational_planner.py:1154`, `:1203`, `:1246`) ⇒ one global scalar, `--relational-decision-budget`, default 4 (`neural_planner.py:180`), set to 12 in E3/E5/E6. |
| T7 | ACTIVE-HOLD/EXPLOIT → TERMINAL(`hold_violated`) | `if not maps:` (`:1574`) | **A verified configuration signature** that stopped mapping. World-driven. |
| T8 | ACTIVE-ESTABLISH → TERMINAL(`contradicted`) | restore executed, configuration did not map (`:1556–1573`) | World-driven, and correctly so: exact outcomes override priors. |
| T9 | any → TERMINAL(`replanned`) | `_terminate_chain` cascade (`:1408–1414`); `active is None` path (`:1441`) | Bookkeeping. |

**Tally.** Of nine transitions, **four are driven by verified world facts**
(T3, T5, T7, T8), **three are bookkeeping cascades** (T9 and the two
successor-drop paths inside `achieve_and_activate`), and **two — the two
that decide whether a mechanism is armed at a given instant — are driven
by counters** (T1 by the decision loop's position, T6 by a decision
count).

### 2.3 The clock, stated exactly

Three properties follow from §2.2 and together they *are* the
misalignment:

1. **The budget's unit is "verified transition", not "opportunity".** T2
   increments identically for a committed decision that walks one cell
   toward the target and for a stagnation restore that throws the agent
   six cells away. Both `_relational_feedback` call sites pass a summary
   and nothing else distinguishes them at the counter
   (`neural_planner.py:25877` commit; `:28773` restore).
2. **Activation has one instant per decision and it is the earliest one.**
   T1 fires at `:21131`, before the proactive entity probe, before
   `_restore_if_stagnant`, before the commit ladder, before the S3 deposit
   gate at `:25438`, before the `decision_committed` emit at `:25663`.
   Anything that terminates a hypothesis after that point leaves the layer
   in NO PLAN for the remainder of the decision **and** re-enters at the
   top of the next decision, where a fresh `propose` runs with
   `achieved_ids=()` (`relational_planner.py:1341–1348`).
3. **A fresh `propose` structurally cannot activate an exploit.** The
   exploit's `InitiationCondition` carries
   `requires_chain_parent_verified=True` (`relational_planner.py:1240`),
   and `initiation_satisfied` checks `chain_parent_id in achieved_ids`
   (`:784–790`) against the empty tuple `propose` supplies. So after any
   exploit termination the *soonest possible* re-arm is: next decision's
   `propose` activates the hold (empty payload) → that decision's commit
   or restore → `advance` → T4 → exploit active. **One full decision of
   guaranteed blindness, by construction.**

Property 3 is not a bug in any single seam. It is the layer's replanning
contract (`_terminate_chain`'s docstring, `relational_planner.py:1393–1397`:
"fallback chains are deliberately NOT auto-activated mid-transition") meeting
the fact that every navigation consumer is gated on ACTIVE-EXPLOIT.

Design §16.4 measured the sequence from telemetry. The code path is:

**The two rows that matter.** Everything else in this table is either
already correct or explicitly deferred. The defects are:

- **(D1) Coverage.** Two of the four restore paths produce no hypothesis
  transition at all. The layer's clock literally skips events the
  incumbent considers decisive.
- **(D2) Blindness.** The expiry rule (T6) consumes the incumbent's most
  informative signal — the committed cell — without reading it. E6's
  budget was consumed *by the approach that produced the arrival*
  (design §16.5), which is the sharpest possible statement that the
  counter is measuring the wrong thing.

## 4. Q2 — Should liveness be event-driven? The rule set

Yes, with a caveat this section makes precise: "event-driven" must mean
*the expiry predicate reads incumbent-generated facts*, not *the expiry
threshold is larger*. §4.53 forbids the latter explicitly ("Re-arming the
budget would be tuning"), and the four rules below are each tested against
that prohibition individually in §4.5.

Four rules, ordered by blast radius (smallest first). They are separable;
§4.6 sequences them.

### R1 — Chain publication scope: an active hold publishes its successor exploit's target cells

**Statement.** While a `hold_configuration` hypothesis is active and its
chain contains an `exploit_configuration` successor whose initiation is
satisfiable on the current verified configuration, `objective_target_cells`
for the active hold returns the successor's `target_cells` rather than
`()`.

**Code shape.** Pure, in `relational_planner.py`. Today
`objective_target_cells:929` reads `hypothesis.realization.payload`. R1
makes it a plan-level query — `published_target_cells(plan) -> Tuple[Cell, ...]`
— so the monolith's `_relational_navigation_objective:19985` asks the plan,
not the hypothesis. Consumers are unchanged; the hold's own payload stays
empty (no data model change, no persisted-option change,
`RealizedOption` untouched).

**What it does at E6's d15/d16.** d15 is unchanged: the exploit still
budget-exhausts, `relational_hypothesis_terminated budget_exhausted` still
lands at seq 82132. At d16 the hold activates as before at seq 82139 — and
now publishes `[[12,11]]`, because the exploit is in `plan.hypotheses`
(proved by the fact that T4 activated it at seq 82664). The S3 gate at
`:25438` therefore evaluates instead of returning `None`, and §16.4 item 5
already established every remaining conjunct: hold signature matches,
position certified, distance 1 ≤ radius 1. **The deposit fires.**

**Why it is not a budget re-arm.** It changes no lifetime. `active_decisions`,
`decision_budget`, T6 and the 12-decision setting are all byte-identical.
The exploit is dead at d16 under R1 exactly as it is today; what changes is
that the *hold* — whose stated purpose in the module docstring is to
sustain a configuration for a dependent successor — stops pretending it has
no objective. The publication window is still bounded by chain existence,
which dies on `hold_violated` (T7) and on the milestone leaving
`remaining_milestone_cells`.

**The honest cost.** R1 does widen the window in which cells are published,
and the S2 restore key reads the same publication. That is a real risk and
§7.2 treats it. The mitigation that makes E7 clean is **per-consumer
publication scope**: R1 is enabled for the deposit gate (S3) only in E7's
primary treatment, leaving S1/S2 reading the hypothesis payload exactly as
in E5/E6. That keeps the treatment's d1–d16 prefix provably identical to
v339's and preserves the single opportunity the experiment rests on (§6.6).

### R2 — Event coverage: the two blind restore paths advance the state machine

**Statement.** `_restore_after_life_loss:26113` and
`_restore_goal_milestone_after_exhaustion:25930` call `_relational_feedback`
with a new summary kind that re-evaluates T7 (hold violation) and T3/T8
(configuration mapping) **without incrementing `active_decisions`**.

**Code shape.** One new `SUMMARY_*` constant in `relational_planner.py`
(alongside `SUMMARY_COMMITTED_DECISION:132` / `SUMMARY_ARCHIVE_RESTORE:133`),
handled in `advance` by routing to the mapping checks and returning
`ADVANCE_CONTINUE` with `active_decisions` unchanged. Two call sites in the
monolith. P1/P4 *selection* is untouched — no seam, no key, no preference.

**What it does at E6's d15/d16.** **Nothing.** Both arms recorded zero
`human_prior_life_loss_confirmed` commits (§16.1 bit 4) and the
goal-exhaustion rollback did not fire in the window. R2 is a correctness
fix with **zero measured effect at this root**, and that is exactly why it
should land separately with its own invariance evidence rather than inside
E7's treatment: bundling a change with no expected effect into an
experiment whose bit 1 is trajectory-prefix identity is pure downside.

**Why it is not a budget re-arm.** It touches no budget at all — the
explicit no-increment clause is the point. It closes D1: the layer stops
having a shorter event list than the incumbent.

### R3 — Progress-conditioned expiry: an exploit does not expire while its distance to target is non-increasing

**Statement.** T6 for an `exploit_configuration` hypothesis fires only when
**both** hold: (a) `active_decisions + 1 >= decision_budget`, and (b) the
minimum Manhattan distance from the verified player cell to the published
target cells has **strictly increased** on each of the last `K` committed
decisions (`K = 2`, a module constant, not a config field). On a
non-increasing distance the budget check is deferred; the counter still
increments, so the rule is a *conjunct added to expiry*, never a reset.

**Code shape.** Pure. `VerifiedTransitionSummary` already carries
`player_cell` (`relational_planner.py:413`); the plan gains a bounded
distance history (length `K+1`, no unbounded state). `exhaust_or_continue`
gains one conjunct.

**What it would have done at E6's d15/d16.** The treatment's measured
Manhattan trace (design §16.3, v339) is

```
d1..d24: 9 7 7 6 8 9 10 6 5 6 4 5 4 3 2 1 4 5 6 6 7 6 6 6
```

At d15 the last two commits were d14 = 3 → d15 = 2, strictly *decreasing*.
Conjunct (b) fails, so T6 defers: **the exploit is alive at d16**, publishes
`[[12,11]]` directly, and the S3 gate fires — the same outcome as R1, by a
different route.

At d18–d20 the trace is 5, 6, 6 — a strict increase at d19 and a plateau at
d20. Under `K = 2` the rule expires the exploit at d20, whereas the count
budget (re-armed by the d16 hold→exploit cycle) keeps it alive to d24.
**R3 shortens the objective's life on the diverging tail and lengthens it
only on a measured approach.**

**Why it is not a budget re-arm.** Three separable arguments, and the
preregistration must score all three or the rule should not ship:

1. **Different input.** A budget re-size is a different constant in the
   same function of the same input (a count). R3 is a function of the
   committed player cell — an incumbent-generated fact that the expiry
   rule does not read today at all.
2. **Two-sided, and measurably so.** A re-size can only extend. R3 extends
   on approach and *contracts* on divergence. E7 must report the count of
   decisions on which R3 extended a lifetime **and** the count on which it
   ended one earlier than the count budget would have. If the second count
   is zero across the window, R3 is behaving as a re-size at this root and
   must be reported as such — a preregistered self-falsification, not a
   post-hoc caveat.
3. **The counterfactual re-size is available and is not equivalent.**
   `--relational-decision-budget 24` would also have kept the exploit alive
   at d15. It would additionally have kept it alive across d5–d8's wander
   (10, 6, 5, 6) and across d18–d24's departure — precisely the instants
   where §4.50 says a live proximity objective does damage. R3 and the
   re-size differ in behavior at ten of twenty-four decisions in the
   measured trace; the scorer can and must compute that difference
   offline, from v339's telemetry, **before** E7 runs.

### R4 — Immediate re-arm on terminal outcomes, replacing next-decision latency

**Statement.** When `advance` returns a terminal outcome, the caller
re-proposes **within the same feedback call** rather than waiting for the
next `decide()` top. Additionally, `propose` accepts the surviving
`achieved_ids` rather than `()` (`relational_planner.py:1341–1348`), so a chain
whose parent is still verified can re-activate its exploit directly.

**What it would have done at E6's d15/d16.** The d15 feedback would
terminate the exploit and immediately re-propose with
`achieved_ids = (establish_id, hold_id)`, satisfying the exploit's
`requires_chain_parent_verified` — so the exploit would be active at the
top of d16, with cells published, and the deposit would fire.

**Why it IS at risk of being a budget re-arm, and what to do about it.**
R4 alone, with T6 unchanged, is a *perpetual* re-arm: exhaust at d15,
re-activate at d15, exhaust at d27, re-activate — the budget becomes a
no-op and §4.53's prohibition is violated in substance while being honored
in letter. **R4 must not ship alone.** It is admissible only paired with a
liveness rule that can actually end an objective on a measured condition
(R3), and even then it is the largest of the four changes: it alters
`propose`'s contract, the replanning discipline documented at
`relational_planner.py:1393–1397`, and the "one activation instant per
decision" property that every prior invariance test has implicitly relied
on. **Recommendation: do not build R4 for E7.** Record it as the fallback
if R1 and R3 both fail, and note that its correct framing is not "re-arm
faster" but "the replanning contract should be per-transition rather than
per-decision" — a planner-architecture change, which §7.3 gives a
preregistered trigger for.

### 4.5 The §4.53 tuning-prohibition test, applied

For each rule: *does it change a constant in an existing expiry function,
or does it change what the expiry function reads?*

| Rule | Changes a threshold? | Reads a new incumbent fact? | Two-sided? | Verdict |
| --- | --- | --- | --- | --- |
| R1 publication scope | No | No (reads the plan's own queue) | n/a — no lifetime changes | **Admissible.** Not a lifetime rule at all. |
| R2 event coverage | No | Yes (two restore events) | n/a — explicitly no budget effect | **Admissible**, and independently correct. |
| R3 progress-conditioned expiry | No — the budget stays 12 in both arms | **Yes** — the committed player cell | **Yes**, and the two-sidedness is a scored bit | **Admissible with the §4.4 R3 item-2 self-falsification bit attached.** |
| R4 immediate re-arm | No, but it *neutralizes* one | No | No — one-sided extension | **Not admissible alone.** Only with R3, and not in E7. |
| (counterfactual) `--relational-decision-budget 24` | **Yes** | No | No | **Prohibited** by §4.53. Named here so the scorer can compute its offline counterfactual as R3's contrast. |

### 4.6 Sequencing by blast radius

1. **R2** lands first, alone, as a correctness fix: two call sites, one new
   summary kind, explicitly no budget effect. Its acceptance evidence is
   an invariance proof (§6.9) plus the observation that the E7 control must
   still reproduce v338 state-for-state. If R2 changes the control at all,
   that is itself a finding — it would mean the layer's blind restores were
   load-bearing — and it must be reported before E7 runs.
2. **R1, scoped to the deposit gate**, is E7's treatment. It is the
   smallest change that closes the measured three-event gap and it is the
   only one that preserves the prefix E7's single opportunity depends on.
3. **R3** is E8's treatment if E7's bit 2 passes and its outcome bit does
   not, or if E7's bit 1 fails for a reason other than R1.
4. **R4** is not built unless §7.3's rewrite trigger has fired, at which
   point it is subsumed by the rewrite.

## 5. Q3 — The intervention-class ruling

**The question, stated precisely.** May a mechanism (concretely: the S3
deposit gate at `neural_planner.py:25438`) obtain its certified target
cells by reading `self.verified_accessibility_records` directly, rather
than from `active.realization.payload["target_cells"]` on a live
hypothesis?

### 5.1 What the two options actually are, in code

The hypothesis payload is not independent knowledge. `_exploit_target_cells`
(`relational_planner.py:1091`) computes

```
milestones = sorted(set(candidate.certified_milestone_cells)
                    & set(state.remaining_milestone_cells))
```

Both inputs are already available to the monolith at the deposit site:
the store at `self.verified_accessibility_records` (`:1315`, class
`VerifiedAccessibilityRecordStore:28837`), and
`remaining_milestone_cells` from `goal_prior.current_slots()`
(`:19537–19545`). A store-read gate is therefore a **re-derivation of the
same function of the same two inputs at a different instant** — not new
information, and not a wider information set. The only thing that differs
is *when* the answer is available: continuously, versus only in
ACTIVE-EXPLOIT.

That framing matters for both sides of the argument, and it is why the
question is genuinely close.

### 5.2 Against — the store read converts hypothesis-driven planning into a standing rule

- **The falsifiability argument, which is the strongest one.** Every WP8
  seam to date has an authority switch and an invariance test proving the
  behavior vanishes when the switch is off. A store-read gate keeps that
  property only nominally: the gate would still be `authority == selection`
  gated, but *nothing in its firing condition would reference the propose /
  score / advance machinery*. Delete `relational_planner.py` entirely,
  keep the store read and the authority flag, and the behavior is
  unchanged. If the behavior survives ablation of the hypothesis layer,
  the hypothesis layer did not produce it — and Gate 4's criterion
  "hypothesis logged before execution" degrades from a cause to a log line
  emitted beside an unrelated mechanism.
- **§4.50 at the standing-rule level.** §4.50 hardened §4.7 from "distance
  rewards fail" to "**any** consistent proximity preference fails", and
  explicitly recorded that the tie-break-not-reward care taken in E3 did
  not save it. A store-read gate is live at every decision the
  configuration matches, which is the definition of consistent. The
  hypothesis's decision budget is currently the *only* thing making the
  preference intermittent, and this proposal removes it.
- **It costs the design one of its five structural defenses.** Design
  §7.3 lists five reasons the navigation mechanism is not §4.7's
  machinery. Item 4 is verbatim: "It is **time-boxed** by
  `relational_decision_budget` and dies with the hypothesis." Under a
  store read, item 4 is false and the document would have to say so. Items
  1, 2, 3 and 5 survive (tie-break not reward; certified sources only;
  gated on a held configuration; never outranks a collection) — but a
  defense that loses a fifth of its structure should say so in the same
  sentence in which it claims the remainder.
- **Roadmap WP8's acceptance gate is written in agent-choice language**
  (§7 WP8 gate items 1 and 4: "The agent *proposes* that changing an
  anonymous object configuration may improve future access"; "It *retains*
  the new configuration across a planning cycle"). A standing rule
  proposes nothing and retains nothing; it reacts.

### 5.3 For — the store is earned knowledge and liveness is bookkeeping

- **The store is not an oracle; it is the agent's own certified output.**
  `AccessibilityRecordProvenance` requires a run id, a preregistration doc,
  a configuration signature, a verification mode, a certification
  predicate, and branch counts (`accessibility_preference.py:135–159`), and
  the content signature covers all of them (`:230`). Records that are not
  `certified_hold` score exactly zero (`:26`, `:425–427`). Reading this is
  reading a result the agent produced under a preregistered probe — the
  same status as any archive branch or learned prototype the planner reads
  without anyone calling it a standing rule.
- **The information content is identical (§5.1).** The hypothesis payload
  adds no fact. What the hypothesis adds is *scheduling* — and scheduling
  is precisely the faculty that four consecutive experiments have measured
  as broken. Conditioning a world-facing gate on a faculty known to be
  defective, in order to preserve a claim about that faculty, is close to
  circular.
- **Liveness genuinely is bookkeeping.** `active_decisions`,
  `max_queue = 4` (`neural_planner.py:176`), chain ordering by lead score,
  and the `propose` early-return at `:19694` are properties of a queue,
  not of the world. §2.3 property 3 — that a fresh `propose` can never
  activate an exploit — is a consequence of passing `()` for
  `achieved_ids` at `relational_planner.py:1347` (`propose`'s activation loop). **A world-facing gate should not be
  conditioned on the argument value of an internal function call.** That
  is the clock misalignment named in the abstract, and roadmap §21's new
  §5 invariant is written against exactly it.
- **The narrower forms are not standing rules.** "May a mechanism read the
  store *at all*" and "may a mechanism read the store *unconditionally*"
  are different questions. A gate that reads the store but is still
  conjoined on a live hypothesis chain existing (even inactive) is
  intermittent, is ablatable, and is not what §5.2 objects to.

### 5.4 Ruling

**A mechanism may NOT take its liveness condition from the record store.
Certified cells stay hypothesis-scoped. R1 — publication scope within a
live chain — is the sanctioned repair.**

The deciding consideration is falsifiability, not purity. §5.3's strongest
point (the store adds no information) is correct and is precisely why the
store read is *tempting*; but it is also why declining it is cheap. If the
information is identical, then R1 delivers the same cells at the same
instant, from a live chain, at the cost of one pure-module change — and it
keeps the ablation meaningful. Paying a small implementation cost to
preserve a falsifiable claim is the trade this project has taken
consistently (design §5.3's redundancy detector; §15.1's decline
telemetry), and the record shows it pays: every FAIL so far was
*interpretable* because the ablation was real.

**Two qualifications, so the ruling is not a dodge:**

1. **The store read gets measured, not just argued.** E7 carries a third
   arm — the **standing-rule arm** (§6.2) — running the store-read gate
   under selection authority. It is scored on no bit. Its sole purpose is
   attribution: if the standing-rule arm's trajectory is identical to the
   hypothesis-scoped treatment's, then at this root the hypothesis layer
   contributes nothing beyond the store read, and §5.2's falsifiability
   objection loses its empirical force — which must then be recorded as a
   finding against the recommended ruling, in the same document, in the
   same pass. The ruling is a decision under uncertainty and it is
   preregistered as revisable on this specific evidence.
2. **A store read remains permitted as a consistency check.** A gate may
   assert that the cells a live hypothesis publishes are a subset of the
   store's certified milestone cells, and refuse (with a named reason) if
   they are not. That reads the store without conditioning liveness on it,
   and it would have caught a whole class of payload defects for free.

### 5.5 What Gate 4 could and could not claim, precisely

**Under the recommended ruling (hypothesis-scoped, R1):**

| Roadmap §7 WP8 gate item | Claimable? | Why |
| --- | --- | --- |
| 1. Proposes that changing a configuration may improve future access | **Yes** | `relational_hypothesis_proposed` precedes every realization step (`:19681`, called at `:21131` before all commit/restore paths), with full per-component score decomposition, and the invariance test proves the behavior is absent at authority `off`. |
| 2. Finds the required controller sequence through exact search | **No** | No seam causes a search (§4.45 mechanism 1; that is E4). The cells come from a record certified in a *prior* run. This must be stated in the Gate 4 claim, not omitted. |
| 3. Verifies the accessibility delta | **Partially** — carried by the record's own certification, not re-verified in-run | The `certified_hold` provenance is real; the in-run verification is a configuration-signature match, not a fresh accessibility probe. |
| 4. Retains the new configuration across a planning cycle | **Yes** | Hold integrity is a reported invariant in every arm since E3; the S2 refusal at E5's d17 is a measured instance of retention winning against the incumbent's preference. |
| 5. Uses the result to reach a subsequent positive visual milestone | **Only if E7's outcome bit passes**, and then only as a *finishing* claim at this root — §4.47/§15.6(g): a second-manipulation capability claim still requires `(8,4)`/`(9,12)`. |
| §12 Gate 4 "counterfactual neutral configuration performs worse within the same budget" | **Yes if bits pass** | The matched-budget control arm is exactly this, with verified-branch equality as a VOID condition. |

**Under the store-read ruling (rejected):**

- Items 1 and 4 would become **unclaimable**. Not weakened — unclaimable.
  There is no counterfactual under which a standing rule declines, so
  "chose" and "retained" have no operational content; the honest claim
  would be "the agent applied previously certified knowledge whenever the
  configuration matched", which is a **knowledge-use** claim.
- Item 5 would still be claimable as an outcome, and item 2 would remain
  unclaimable for the same reason as above.
- Net: the store read could close Gate 4's *outcome* criteria while
  emptying its *deliberateness* criteria — and deliberateness is the whole
  content of Gate 4 (roadmap §12: "Deliberate preparation"). Passing a gate
  by removing the property it was written to detect is not a pass.

A new selector, `NeuralPlanningConfig.relational_lifecycle` /

check any arm in this family has had.

### 6.4 The preregistered bits (fixed; **ANY mixed outcome = FAIL**)

**Bit 1 — SUPPLY AND PREFIX.** All three conjuncts.

- **(a)** The treatment's committed state ids for d1–d15 equal **v339's**
  exactly. (Not merely equal to this run's control — equal to the prior
  treatment, because §6.3 predicts byte-identity up to the deposit.)
- **(b)** The control's 24 committed state ids reproduce **v338's**

- **(c)** Archive geography not narrowed: `treatment_min_column <=
  control_min_column` and `treatment_max_column >= control_max_column`,
  with the columns-6–12 / 44-vs-43 reference reported alongside, and S3
  deposits counted separately as well as inside the total. One-sided, for
  §13.4's reason: E3 failed by narrowing, and a treatment that deposits
  further east must not be scored FAIL for it.

**Bit 2 — PUBLICATION AT THE DECISIVE INSTANT.** Both conjuncts. *This is
the bit that discriminates E7 from E6, and it is scored on the mechanism's
own telemetry, not on the outcome.*

- **(a)** At the treatment's first committed decision with Manhattan
  distance ≤ 1 to `(12,11)` under the hold signature, the S3 gate emits an
  event of **either** kind — i.e. `_relational_navigation_objective()` is
  not `None`. E6's exact defect was the *absence* of any event at d16;
  a decline with a named reason would be a different, informative result
  and passes (a).
- **(b)** That event is `relational_navigation_deposit_added`, with
  `deposit_distance <= 1` and its `hold_configuration_signature` equal to
  both the objective's hold signature and the arm's
  `configuration_signature` at that instant.

**Bit 3 — CANDIDATE REACHABLE.** The deposited branch appears in a later
restore's eligible set: some `relational_navigation_restore_selected`
after the deposit reports the deposited cell among the arm's archive with
`hold_matching_candidates` strictly greater than E6 recorded at the
corresponding instant, **or** the deposit is itself selected. §15.6(d)'s
`recovery_distinct` blind spot is re-declared: a position deposited at `d`
is invisible to a restore at `d+1` while the agent still stands on it, so
E7 may need the **second** restore after the deposit. A bit-3 failure
attributable to `recovery_distinct` is reported as an
**archive-eligibility** finding, naming the filter from the arm's own
telemetry — never as a near miss.

**Bit 4 — OUTCOME.** Within 24 decisions the treatment collects `(12,11)` /
`(192,176)` (evidenced by `[192,176]` entering
`human_prior_collected_heart_slots` on a `decision_committed`) and the
control does not. If both collect it, bit 4 FAILS: the discriminator would
be dead and a speedup is not the claim.

**Bit 5 — SAFETY.** The treatment records no more
`human_prior_life_loss_confirmed` committed decisions than the control.

and under R1 it is expected at d15 and is not supposed to matter, which is
the whole hypothesis.

### 6.5 Readings fixed now, before the result

- **No-publication null.** If bit 2(a) fails — no gate event at the
  decisive instant — R1 did not do what §4.4 claims and the reading is
  that the exploit successor was **not in `plan.hypotheses`** at that
  decision (a `max_queue`/ordering fact), which the
  `relational_hypothesis_proposed` queue dump settles without a further
  run.
- **Declined-at-the-instant reading.** If bit 2(a) passes with a
  *decline*, the reason code names the failing conjunct
  (`held_configuration_absent`, `position_not_certified`,
  `position_unavailable`, `already_archived`) and the finding is about
  that conjunct, not about liveness. This is a genuinely new sub-case E6
  could not produce.
- **Deposited-but-ineligible.** Bit 3 fails ⇒ archive-eligibility finding,
  filter named (§15.5's pattern, unchanged).
- **Held-and-still-not-collected.** If bits 1–3 pass and bit 4 fails, the
  agent stood on or beside the milestone, the position was held and
  restorable, and it still did not step onto the cell. **That is §7.3's
  rewrite trigger**, and it is written here so it cannot be re-narrated as
  a sixth seam opportunity afterwards.
- **Attribution null.** If the standing-rule arm is trajectory-identical
  to the treatment, record it against §5.4's ruling as specified — in the
  same pass, not deferred.
- **Agreement null.** If every `relational_navigation_restore_selected`
  carries `differs: false`, that is a redundancy finding of the
  §4.43/§4.45 family, reported as such and explicitly **not** as
  under-powering and **not** as grounds for a further lever.

### 6.6 Honest power analysis, before the run

**(a) There is no sampling variance, and "power" here means opportunity
count.** Runs are deterministic (the four-run invariance chain proves it).
The relevant question is: at how many instants can the mechanism fire?

**(b) The opportunity count for bit 2 is ONE.** From v339's measured
Manhattan trace, exactly one committed decision (d16, distance 1) is inside
the radius-1 gate. The nearest others are d15 at distance 2 and d17 at
distance 4 — both outside, and §16.5 already established that widening the
radius is forbidden and would supply nothing new, since `(12,7)`–`(12,9)`
were already candidates and the d17 restore already selected `(12,7)`.
**E7's central bit rests on a single instant.** This is stated up front
because it dictates everything else in the design.

**(c) Therefore the dominant FAIL mode is opportunity destruction, and the
design is built to avoid it.** Any change that perturbs the treatment's
trajectory before d16 removes the only instant at which bit 2 can be
scored. That is exactly why R1 is scoped to the deposit gate alone (§6.3)
and why R2 and R3 are held back (§4.6). Under the full R1 — publishing to
S1/S2 as well — the S2 key would become live at restore instants where it
currently falls open (the exploit was dead d15–d16 and after each budget
cycle), the restore selection could change, and the d16 geometry would not
recur. **Pre-declared: if bit 1(a) fails, the reading is "liveness widened
the intervention window and moved the approach" — a FAIL with a named
mechanism, not a VOID, and not grounds for re-scoping and re-running.**

**(d) Bit 4's opportunity count is also small and is not improved by more
decisions.** §14.6 and §16.6 both recorded it: the treatment was moved off
the target at d17 with seven decisions remaining and never returned. A
larger `--decisions` extends a trajectory that has already left. E7 does not
raise the decision count and must not.

**(e) What R1 cannot show.** A PASS demonstrates that a chain-published
objective closes the E6 gap at this root. It does **not** show the planner
can cause a search (E4, §4.45 mechanism 1), does not validate R3, and does
not demonstrate a second manipulation.

**(f) The R3 offline contrast, computable before E7 runs and required as a
precondition for E8.** From v339's telemetry alone, compute (i) the
decisions on which R3 would have extended the exploit's life beyond the
count budget, and (ii) the decisions on which R3 would have ended it
earlier. §4.4 R3's two-sidedness claim is either supported by that
computation or it is not, and it costs zero emulator time to find out. If
(ii) is empty, R3 is a re-size at this root and E8 does not run.

### 6.8 Health-check rule (learnings §4.52)

**Health-check the arms by the run's own telemetry — event growth and
expected seq milestones — never by external process pattern matching.**
Concretely, and stated before the run so a bad premise cannot become a bad
diagnosis:

- The process is `python -m lolo_agent.neural_run` — **underscores, module
  form**. A hyphenated `pgrep` pattern can never match and its silence is
  not evidence of death.
- The first `decision_committed` lands at seq ≈ **75,742** in every arm of
  this family. **Zero committed decisions at 6k events is on-profile, not
  a death.**
- The health signal is monotone growth of `events.jsonl` and arrival at
  the expected seq milestones, read from the run's own log.
- Two signals that share an author are not corroboration (§4.52).
- The interpretation rule is fixed in advance: **a crashed arm is VOID,
  not FAIL** (VOID condition 6), so no diagnosis under time pressure can
  convert an operational failure into evidence.

### 7.2 Does an event-driven lifetime rule smuggle in a consistent proximity preference?

The question is the right one to ask and the answer differs per rule.

- **R1 — no, and this is checkable.** R1 changes *which hypothesis's
  payload is read*, not any ordering. Scoped to the deposit gate (§6.3) it
  adds a **candidate** and no term — the same property §15.1 established
  for S3 and which E6's measurement confirmed (the treatment differed from
  E5's by exactly twelve log lines and zero behavior). Bit 1(a)'s
  prefix-equality-to-v339 is the direct test: if R1 had smuggled in an
  ordering effect, d1–d15 could not reproduce.
- **R1 unscoped — yes, at one remove, and that is why it is not in E7.**
  Publishing to S2 as well would lengthen the window in which a
  proximity-ranked restore key applies. S2 is a proximity preference over
  restore destinations; extending its live window is extending a proximity
  preference's coverage without adding a term. §4.50's lesson is that the
  care taken to make E3's mechanism a tie-break rather than a reward did
  not save it — so "no new term" is not a sufficient defense, and
  "unchanged term, longer window" deserves the same suspicion.
- **R3 — yes, structurally, and it must be scored on geography.** "Do not
  expire while distance is non-increasing" is a proximity-conditioned
  *lifetime*, and lifetime multiplies into every consumer. It is one level
  up from the thing §4.50 killed. Two things make it testable rather than
  forbidden: (i) it is two-sided, contracting on divergence (§4.4 R3,
  §6.6(f)); (ii) bit 1(c), archive geography, is the direct instrument —
  E3 failed it (columns 6–8 vs 6–12) and E5/E6 passed it. **Pre-declared:
  if an R3 arm narrows the treatment's archive columns relative to the
  control, that is §4.50 recurring at the lifetime level and R3 is
  abandoned, not tuned.**
- **R4 — the question does not arise, because R4 is inadmissible on other
  grounds (§4.5).**

### 7.3 The next failure could be one level deeper again — the preregistered rewrite trigger

Five levers are measured and each failed for a distinct named reason
(§16.7). E7 is the sixth. The pattern to date is genuine narrowing, not
whack-a-mole, and §4.53 argued that correctly. But narrowing has an
endpoint, and the decision to stop bolting onto the incumbent planner must
be made by a rule stated in advance rather than by fatigue. **Three
triggers, any one of which fires the rewrite decision:**

**Trigger A — the failure moves inside the incumbent's own commit ladder.**
If E7's bits 1–3 pass and bit 4 fails, the agent will have: stood on or
beside the certified milestone, under the held configuration, with the
position deposited, restorable, and reachable by a working key — and still
not collected it. Every remaining explanation lies inside the P5 ladder
(`neural_planner.py:23180–23500`), which has **no tier that references a
target cell** (design §3.2) and whose novelty-keyed
`human_prior_semantic_frontier_choice` is what does the wandering. No seam
on the hypothesis layer can address that; the layer would have delivered
everything it can deliver. **The response is not a seventh seam** — it is
either a planner rewrite that gives the commit ladder an objective-aware
tier as a first-class concept, or a move to representation depth
(WP2/WP3 integration), decided on the evidence in that report.

**Trigger B — the seams stop being independently ablatable.** If E7's bit
1(a) fails — the treatment's prefix diverges from v339 before the
intervention instant — despite R1 being scoped to a gate that adds a
candidate and no ordering, then the layer's effects have become entangled
with the incumbent's schedule in ways the authority switch no longer
isolates. The "bolt-on with an authority switch, proven inert when off"
model would have expired, and with it the entire E-series' claim to
interpretability. A rewrite is then required not for capability but for
measurement.

**Trigger C — a repeated failure reason.** The project's own bookkeeping is
the stopping rule: each of the five falsifications has a *distinct* named
mechanism, and that distinctness is what makes the sequence convergence
rather than repetition. **If a sixth or seventh lever fails for a reason
already on the list** — redundancy with the baseline (§4.43/§4.45), no
opportunity to act on (§4.45/§4.46), supply starvation (§4.50), a
candidate that does not exist (§4.51), or an objective absent at the
instant (§4.53) — then the narrowing has stopped and the bolt-on approach
should be replaced. One repeat, not two: a second repeat would be the
fatigue decision this trigger exists to prevent.

**What "rewrite" means, so the trigger is not a threat without a
referent.** Not a rewrite of `neural_planner.py` wholesale. It means:
promoting the commit ladder and the restore decision into an explicit,
testable policy object with a declared objective input — the thing every
seam so far has approximated from outside — and moving the hypothesis
layer's replanning contract from per-decision to per-transition (R4's
correct framing, §4.4). That is a WP-scale piece of work and it must be
planned as one, with roadmap and learnings amendments, not smuggled in as
a seam.

### 10.8 Health-check rule (learnings §4.52), fixed before the run

- The process is `python -m lolo_agent.neural_run` — **underscores, module
  form**. A hyphenated `pgrep` pattern can never match and its silence is
  not evidence of death. **Health is checked by the run's own telemetry
  only**: monotone growth of `events.jsonl` and arrival at the expected
  seq milestones.
- The first `decision_committed` lands at seq ≈ **75,742** in every arm of
  this family. **Zero committed decisions at 6k events is on-profile, not
  a death.**
- Two signals that share an author are not corroboration.
- **A crashed arm is VOID, not FAIL** (VOID 6), so no diagnosis under time
  pressure can convert an operational failure into evidence.

### 10.9 Scorer

A single deterministic scorer walks each arm's `events.jsonl` once, applies
§10.4 verbatim, and writes `experiments/lolo1-wp5/e7-gate4-report.json`
with a canonical-JSON `digest_sha256` over the body (digest field
excluded). Run end-to-end **twice**; both reports must be byte-identical.
**It is validated against v338 and v339 first**: it must reproduce §16's
verdicts exactly — the 12 declined-deposit instants with reasons, the zero
deposits, the columns-6–12 geography with 44/43 deposits, the 8 restore
instants with 2 differing, the `hold_matching_candidates` series
`1,3,3,6,6,5,4,3`, and the "never collected `(192,176)`" reading.

Distance metrics: **Chebyshev** for the §4.47/§4.48-comparable traces,
**Manhattan** for the mechanism's own `deposit_distance` /
`selected_distance`. Bit 2(b) is scored on the mechanism's own Manhattan
figures as emitted; bit 4 is metric-free.

### 10.10 The §6.6(f) R3 offline contrast — computed before E7 ran

Zero emulator cost, from v339's recorded telemetry alone, as §6.6(f) and
§9 item 2 require. The simulator reproduces the measured exploit lifecycle
first (activation at the end of d3, one `advance` per decision, terminal
`budget_exhausted` at d15 — exactly 12 transitions, matching the run) and
then re-runs it with R3's conjunct (b) added, `K = 2`, budget unchanged at
12.

| Model | Decisions on which the exploit objective is live |
| --- | --- |
| Count budget (**measured**, v339) | 4–15, **17–24** (dead at 16) |
| R3 (budget 12 + conjunct (b)) | 4–18, **20–24** (dead at 19) |
| `--relational-decision-budget 24` (the prohibited re-size) | 4–24 |

- **(i) R3 extends beyond the count budget at exactly one decision: d16** —
  which is precisely the decisive instant. R3 would have reached E7's
  outcome by a different route, as §4.4 predicted.
- **(ii) R3 ends the objective earlier than the count budget at exactly
  one decision: d19** (m d17=4 → d18=5 → d19=6, two strict increases).
  **(ii) is non-empty, so R3 is not a re-size at this root and §6.6(f)'s
  E8 precondition is met.**
- **Correction to §4.4 R3 item 3, recorded rather than quietly dropped.**
  The design asserted that "R3 and the re-size differ in behavior at ten
  of twenty-four decisions in the measured trace". Under the rule *as
  literally stated* they differ at **one** decision (d19), not ten: the
  re-size keeps the objective alive continuously from d4, and R3 differs
  from it only where conjunct (b) fires. §4.4's own worked example
  ("expires the exploit at d20") is likewise off by one — the two strict

  be v339's. The contrast is therefore evidence about the *rule's shape*,
